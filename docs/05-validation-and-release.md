# 验收、测试与发布规范

本轮只校验规划文档、源码路径、版本和 Git 基线。下面是执行模型后续必须完成的验证，不代表已经通过。

## 1. 验证层次

| 层次 | 验证内容 | 方法 |
| --- | --- | --- |
| 纯逻辑 | 帧解析、事件转换、能力判断、状态归并 | 单元测试，固定数据和时钟 |
| 契约 | Electron IPC、运行时命令、host bridge、会话 DTO | 生产者与消费者契约测试 |
| 进程 | OMP 启停、退出、超时、资源回收 | 可控假进程及真实 OMP 无费用启动 |
| 工具 | 拒绝前无副作用、批准一次、取消实际终止 | 隔离目录 + 本地 mock 模型驱动真实工具 |
| 应用 | 新会话、输入、审批、停止、恢复和切换 | 从用户入口开始的组件/集成测试；跨进程风险使用针对性 Electron E2E |
| 发布产物 | 独立运行时、安装、离线启动、资源路径 | 打包后测试，不能只证明 dev 模式工作 |

运行上游已有测试之前先阅读其前置条件。不要将需要线上账号、真实模型或用户实际数据的套件混入普通自动化。

## 2. 必须覆盖的行为矩阵

| 类别 | 成功场景 | 失败/边界场景 | 完成阶段 |
| --- | --- | --- | --- |
| 启动 | 指定 OMP 版本就绪，模型/命令查询成功 | 可执行文件缺失、错误版本、原生模块缺失、启动超时 | M1-M2 |
| 协议 | 分块读取 NDJSON、v1/v2 正常消息 | UTF-8 跨块、非法 JSON、分片丢失/重复、超限、stdout 污染 | M1-M2 |
| 消息 | prompt、文本/思考、完整结束 | 模型错误、流中断、收到应答但尚未结束、重复终止事件 | M3 |
| 工具 | 开始、进度、结果、多个工具调用 | 未知工具、大结果、执行报错、ID 冲突或结果晚到 | M3 |
| 权限 | 批准后执行一次 | 拒绝/过期/断连无副作用，跨会话审批无效 | M1/M3 |
| 交互问题 | 选择、输入、确认 | 用户取消、问题撤回、进程退出、重复回答 | M3 |
| 取消 | 回复生成中停止，工具执行中停止 | 子代理/后台进程残留、忽略 abort、强杀回退 | M1/M3 |
| 会话 | 创建、命名、恢复、归档、分支 | 文件丢失、旧版本格式、损坏、崩溃中断和迁移失败 | M4 |
| 项目隔离 | 两项目并行、前台切换 | cwd 漂移、错误权限根、消息串入另一会话 | M4 |
| 模型/凭证 | 独立模型配置和运行时注入 | 无认证、无效模型、Key 泄露、隐式继承全局配置 | M4 |
| 子代理 | 父子关系、进度、详情和结束 | 孤立任务、重复编排、父停止后的子任务行为 | M5 |
| 插件/MCP | 支持的插件类别和单次工具注册 | 不兼容扩展、重复服务、工具命名冲突和能力越界 | M5 |
| Plan/Goal | 已映射的状态和审批转换 | 同名不同语义、未经批准执行、重启后旧授权重用 | M5 |
| 发布 | 无全局 Bun/OMP 环境启动 | ASAR/Resources 错误、路径空格中文、离线、更新源串用 | M6 |

## 3. 推荐测试数据

使用临时示例项目：一个小 TypeScript 程序、一个可通过/失败切换的测试、一个允许编辑的文件、一个禁止写的相邻目录。不要在用户的业务代码上验证拒绝、删除和恢复行为。

本地 fake provider 返回确定的文本和工具调用，用于驱动完整 OMP 链路。协议 fixtures 取自真实输出并脱敏；合成异常帧用于故障测试。两类 fixture 明确区分。

所有会话、模型配置、日志和数据库都放入该次运行的独立目录。磁盘和进程副作用断言是审批测试的核心，不能只断言“显示了拒绝卡片”。

## 4. 各阶段关键验收流程

### M0 原应用基线

启动隔离的开发版，打开示例项目，进入设置与会话。记录界面尺寸及关键布局。原有构建或测试失败必须注明复现命令和与本任务的关系。

### M3 第一条 OMP 编码任务

1. 新建 OMP 会话，选择测试模型。
2. 要求读取示例文件并修复一个小问题。
3. 流式显示过程和工具；第一次写请求拒绝，断言文件未变。
4. 重新请求并批准，断言文件只修改一次。
5. 运行项目测试并展示结果。
6. 启动一个受控长任务后停止，断言后台进程结束且界面状态正确。

### M4 恢复与并发

关闭应用后重新打开，恢复同一 OMP 会话；同时打开另一个项目执行独立任务。确认消息、目录和模型各自独立。模拟 OMP 崩溃，不得自动重跑上一条写文件指令。

### M6 安装产物

在隔离账户或没有全局 OMP/Bun 的环境，从实际安装包打开；完成项目打开、消息、工具、停止和恢复。确认没有访问 PI-Desktop 的数据库和更新源。

## 5. 视觉与交互验收

首期以原 PI-Desktop 为基线，允许为引擎、审批、OMP 特有工具增加必要控件。保持现有图标库、i18n 和组件规范。

检查常用桌面窗口、最小支持窗口、窄侧栏、长文件名、中文路径、长工具输出及缩放。验证焦点、滚动、自动跟随、复制、键盘输入、禁用态和错误恢复，无重叠、遮挡或布局跳动。

优先使用上游现有组件测试和针对性 Electron E2E。遵守 `app/AGENTS.md` 对 `verify:ui:*` 的专门限制，不将这类命令当作默认验证步骤。

## 6. 基础验证命令

从 `app/` 执行，先 `nvm use 24`。这些命令是否全部需要由实际修改范围决定；M0 应记录最小基线，涉及宿主行为时才增加相应 Rust 验证。

```bash
pnpm build:js
pnpm --filter @pi-desktop/desktop typecheck
pnpm lint
pnpm -r --if-present test
cargo fmt --check
cargo test -p host-core --locked
cargo clippy -p host-core --all-targets
```

OMP 相关测试使用其锁定版本中实际存在的脚本。新增包在 M2 确定名称后再加入精确的 `pnpm --filter ... test` 命令。禁止把拟定命令写成“已经运行成功”。

## 7. 验证记录格式

每个阶段在 `docs/validation/` 新建对应 Markdown，至少记录：

- 系统架构、Node/pnpm/Bun/Rust 版本、两份源码 SHA。
- 当前差异是否已提交；如未提交，保留对应 diff 标识或测试时的状态。
- 每个执行命令、运行目录、退出码、关键结果。
- 验证的具体行为和测试文件，用户流程对应关系。
- 截图/日志/fixture 路径；样本必须脱敏。
- 未执行项、原因、剩余风险和下一阶段条件。

## 8. 发布前检查

- [ ] productName、appId、图标和应用数据目录独立。
- [ ] OMP、Bun/桥接、原生模块的版本与目标架构固定。
- [ ] 无全局开发工具也能启动打包产物。
- [ ] 更新功能禁用或指向新产品自己的正式发布源。
- [ ] 实际凭证存储、数据库、会话、日志与原应用隔离；有系统密钥存储时同时核对其命名。
- [ ] 许可证、版权和第三方声明完整，履行相应源码义务。
- [ ] 未支持功能和平台有明确说明。
- [ ] 签名、公证及权限声明与实际发布目标一致。
- [ ] 会话升级备份与旧版本回退路径经过验证。
- [ ] 真实模型烟测的提供方、模型及预算由用户明确指定。

安装包构建成功不等于获得了发布授权；本规划不要求执行模型自动公开发布。
