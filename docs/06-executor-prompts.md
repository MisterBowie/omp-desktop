# 交给执行模型的任务说明

建议始终让模型打开整个 `omp-desktop/` 工作区，以便同时访问计划、桌面源码和 OMP 参考源码。不要只打开 `app/` 而遗漏上层计划。

每一轮只执行一个阶段或明确的任务编号。用户可以调整优先级；任何会影响权限、会话或协议的改变需要同步设计和验证。

## 首轮：环境与基线

```text
请在当前 OMP Desktop 工作区执行 M0（T01-T03）。

先阅读 AGENTS.md、HANDOFF.md、docs/00-scope-and-decisions.md、
docs/01-source-audit.md、docs/03-implementation-plan.md 和
docs/07-environment-and-upstream.md，再阅读 app/ 的适用执行规范。

我已安装 NVM 和 Node 24，使用 nvm use 24，不要重复安装 Node，
不要更改全局默认版本。检查并准备锁定版本所需的 pnpm、Bun、Rust。
依赖按上游锁文件安装，先核对安装和构建脚本。

本轮目标是：原 PI-Desktop 可复现构建；开发数据、凭证存储、更新源
与现有应用隔离；OMP 能在隔离配置下完成无费用的协议启动。
记录原桌面代表性 UI 和测试基线。不开始全面替换引擎，不调用真实付费模型。

发现阻塞时先完成不依赖它的工作。将真实命令、结果及未完成项写入
docs/validation/M0-baseline.md，更新 docs/04-task-board.md 和 HANDOFF.md。
不要自动提交、推送、发布或修改 OMP 参考仓库。
```

## 第二轮：接入与权限实验

```text
请执行 M1（T04-T07），前置是 M0 已完成。

依据 docs/01-source-audit.md 定位真实 RPC、SDK、扩展事件、
host_tool_*、子代理、会话恢复和配置发现入口。
完成 docs/03-implementation-plan.md 的 E01-E09 实验。

使用隔离目录、本地 fake provider 和真实 OMP 内部工具链路验证；
普通 RPC 的交互提问不等于权限审批，set_host_tools 也不等于
所有原生工具均受宿主控制。必须证明拒绝发生在副作用之前。

优先验证 rpc-ui 加 OMP 原有审批 wrapper/受信扩展。输出真实脱敏协议 fixtures、RPC/rpc-ui/SDK/ACP 能力对照、
取消与恢复实验结果，并通过 ADR 选择一条主要生产接入路径。
如果原生 RPC 不足，完成独立 SDK bridge 的最小证明。
本轮不重写界面、不展开全部业务功能、不调用付费模型。

更新 docs/validation/M1-compatibility.md、docs/decisions/001-omp-transport.md、
任务看板和交接说明。不可把仅从代码推断的能力标为已运行验证。
```

## 第三轮：运行时边界

```text
请执行 M2（T08-T10），沿用已通过 M1 的 ADR。

保留现有 Pi 引擎行为，提取最小会话运行时边界；新增 OMP adapter、
进程监督、真实协议转换和必要能力字段。使用已有 shared/IPC/存储模式。
不要在 main/index.ts、app-store.ts、ChatTranscript.tsx 堆积新分支。

新会话能够选择引擎，既有会话仍归属 Pi。未支持能力不能进入旧引擎路径。
完成启动、超时、异常退出、挂起请求清理和应用数据隔离测试。
将改动和验证记录到 docs/validation/M2-runtime.md，更新看板及 HANDOFF.md。
```

## 第四轮：聊天、工具与停止

```text
请执行 M3（T11-T13）。保持 PI-Desktop 已有布局和交互风格。

接通 OMP 文本、思考、工具、用量、结束和错误事件；复用已有展示，
保留 OMP 原始结构的有类型扩展，对未知工具提供通用可展开结果。
接入已经证明的执行前权限桥和用户提问，区分这两种交互。

实现真正的后台取消和晚到事件隔离。按验收文档跑通
“读文件 -> 拒绝写入无副作用 -> 批准后写入 -> 测试 -> 停止长任务”。
添加代表性用户路径测试，以及跨进程边界需要的针对性 Electron E2E。
记录 docs/validation/M3-workflow.md，更新看板和交接。
```

## 第五轮：可靠会话与模型配置

```text
请执行 M4（T14-T16）。

明确 OMP 原生会话与桌面元数据的单一写入责任，实现版本化会话引用、
旧 Pi 会话兼容、恢复、命名、归档及已验证的分支操作。
接入桌面模型配置与受控认证注入，避免自动混用用户全局 OMP 配置。

验证两项目并发、侧栏切换、崩溃重启、文件缺失、迁移失败和晚到事件。
不得自动重放产生副作用的旧 prompt 或复用上次启动的审批。
记录 docs/validation/M4-persistence.md，更新看板和交接。
```

## 后续：逐项开放能力

```text
请执行 M5 的指定任务：<填 T17、T18、T19 或 T20>。

先核对当前能力表，明确此次功能由 OMP、桌面或宿主的哪一方负责。
不要重复注册 MCP、重复启动子代理或把 OMP 工具换成同名旧 Pi 工具。
先完成完整用户路径和失败状态，再开放入口。
所有专用 UI 沿用现有组件、图标与 i18n；同步规格、测试和兼容性说明。
完成后更新阶段验证文档、看板和 HANDOFF.md。
```

## 打包任务

```text
请执行 M6（先 T21-T22），目标是 macOS arm64 安装产物。

固定 OMP 与所需运行时/原生依赖，按 ADR 选择打包方式；生产启动不
依赖全局 Bun/OMP，也不在线下载 latest。核对 Resources、ASAR 外部资源、
路径中文和空格、进程树退出、独立 userData/凭证存储/appId 和更新源。

保留许可证与版权说明，在无全局 OMP/Bun 的环境测试实际安装产物。
没有签名证书时如实交付未签名的开发构建，不绕过系统安全设置。
不自动发布。更新打包验证记录、看板及交接。
```

## 每轮结束时要求模型回答

```text
1. 已完成的任务编号及可观察结果。
2. 修改文件和关键接口/数据责任的变化。
3. 实际执行的验证、结果与证据文件。
4. 尚未完成的内容及原因。
5. 下一轮应执行的任务编号和前置条件。
```

上述任务书不会授权模型替用户开通付费服务、提交远程 PR 或公开发布。若用户另行明确授权，按实际授权继续。
