# 分阶段实施计划

顺序：`M0 -> M1 -> M2 -> M3 -> M4 -> M5 -> M6 -> M7`。M0-M4 完成后得到基本可用的开发版；M5 逐项开放 OMP 差异能力；M6-M7 才面向日常安装和发布。

不要一次性把整份计划交给模型实现。每轮指定任务编号，完成当前阶段的证据和交接后再继续。

## M0：建立可复现开发基线

目标：证明原 PI-Desktop 能在当前机器上构建，并为新应用隔离数据。

输入：两份已拉取的源码、`source-baseline.json`、现有 Node 24。

步骤：

1. 阅读仓库执行规范，核对 SHA、Git 状态和 `.codegraph/`。
2. `nvm use 24`；pnpm 对齐 10.34.5。桌面准备 Rust 稳定工具链；OMP 源码构建按根配置准备 Bun >=1.4 和 `nightly-2026-08-12`，最终锁定实测版本。
3. 分别安装锁文件指定的依赖；先阅读 install/build 脚本，使用包管理器现有流程，不手改锁文件。
4. PI-Desktop 先运行静态构建和既有最小测试，记录原始失败。不要把上游已有故障算成适配回归。
5. 确认开发用 userData、数据库、实际凭证存储和更新源；优先核对现有 `PI_DESKTOP_DATA_DIR` 与 `applyDevelopmentUserData`，通过已有配置或小范围代码调整隔离，不命中用户实际数据。
6. 启动开发版，记录项目列表、会话页、模型设置、插件页等代表性界面，作为保留 UI 的基线。
7. 在隔离目录验证 OMP 版本与无模型调用的协议启动；源码启动所需的 Rust 原生模块按 OMP 流程构建。

交付：`docs/validation/M0-baseline.md`、隔离配置、环境记录、原始测试状态。

退出条件：能够用记录的命令复现原桌面构建和 OMP 协议启动；测试没有访问真实用户会话或产生模型费用。环境缺项只能标记为未完成。

## M1：兼容性实验和路径定案

目标：用源码和最小实验确定生产接入方式，解决最危险的不确定性。

先阅读 `01-source-audit.md` 指向的 RPC、会话 SDK、扩展钩子、宿主工具、主进程监督和权限实现。实验置于 `app/experiments/omp-bridge/` 或符合上游约定的测试目录，不接入产品主流程。

必须完成以下实验：

| 实验 | 输入与操作 | 必须得到的证据 |
| --- | --- | --- |
| E01 协议启动 | 锁定 OMP，隔离配置与 cwd，读取 ready，按真实定义协商版本 | ready/response 的脱敏样本、版本和帧限制 |
| E02 消息循环 | 本地假模型依次返回文本、思考和一个受控工具调用 | 事件序列、prompt 应答时机、真实回合完成信号 |
| E03 交互 | select/confirm/input、取消和超时 | UI 请求的关联 ID、响应结构与 pending 清理 |
| E04 权限阻断 | 请求写隔离文件、执行命令，分别批准和拒绝 | 拒绝时无文件/进程副作用，批准后只执行一次 |
| E05 取消 | 工具执行中 abort、桥接退出、终端/窗口关闭 | 父任务、子任务和后台进程的终止证据 |
| E06 持久化 | 新建、命名、关闭、按路径恢复、分支 | 原生会话位置、身份映射和恢复结果 |
| E07 配置隔离 | 配置模型、规则和 MCP，使用空隔离根 | 没有读取/改写用户全局凭证和会话的证据 |
| E08 子代理与工具桥 | 宿主工具调用与取消，子代理订阅和快照 | `host_tool_*`/子代理事件覆盖范围，原生工具是否另走入口 |
| E09 传输边界 | 半帧、超长帧、v2 分片、非法消息和进程退出 | 重组、报错和挂起请求的确定行为 |

E02/E04/E05 使用本地 mock provider 或可控 SDK 测试边界驱动真实内部执行流程。不能把所有内部工具都 mock 掉，再声称权限覆盖已证明。无费用验证完成后，才考虑用户指定测试模型的烟测。

记录 RPC、rpc-ui、SDK、ACP 的实际能力差异。优先验证 rpc-ui 加原有审批 wrapper/受信扩展，不先绕过它另建审批系统。已有 `set_host_tools` 可以注册宿主工具，但不自动证明所有 OMP 原生工具都经过宿主权限层。

交付：`docs/validation/M1-compatibility.md`、脱敏协议 fixtures、可重复实验命令、`docs/decisions/001-omp-transport.md`，同步范围文档 D01-D07。产品代码改变冻结架构时，按上游规范在 `app/docs/adr/` 另写英文 ADR，并在工作区决策记录中链接。

退出条件：选择一条主要接入路径；消息、恢复和执行前权限链路都有证据。若 RPC 不足，完成 SDK bridge 的最小验证再进入 M2；不是简单注明“以后接权限”。

## M2：最小运行时边界与应用身份

目标：让桌面能容纳 OMP，同时证明原 Pi 行为没有被破坏。

步骤：

1. 从现有 sidecar/会话路由抽出真正需要的接口，保持现有 Pi 实现行为不变。
2. 在 shared 中定义引擎 ID、最小能力清单和版本化会话引用，覆盖生产者和消费者。
3. 新增 OMP runtime 包并纳入 pnpm workspace；Bun 或 OMP 可执行文件由进程监督器独立管理。
4. 实现传输、启动、退出、错误、取消、资源回收及 mock OMP 子进程。
5. 新会话可选择引擎，现有会话仍为 Pi；OMP 未通过验收的入口按能力关闭。
6. 完成独立应用数据标识及开发更新禁用的测试，避免新旧产品互相覆盖。

主要边界：Electron main 的 sidecar/session 模块、`packages/shared`、新 runtime 包、会话元数据层。不要将新逻辑堆入 `main/index.ts`、`app-store.ts` 或 `ChatTranscript.tsx`。

交付：接口、OMP 空闲进程可管理、原 Pi 对照测试、引擎选择和隔离验证。

退出条件：两个引擎可被正确路由；崩溃和关闭无挂起请求；未开放功能不会误进入原 Pi 执行路径。

## M3：端到端对话与工具执行

目标：在保留的桌面 UI 中完成一条真实 OMP 工作流。

步骤：

1. 映射 prompt、文本/思考增量、工具开始/更新/结束、用量、结束和错误。
2. 工具卡片复用现有展示；对 OMP 结构保留 typed metadata；未知工具采用通用展开视图。
3. 接入 M1 证明的执行前权限桥，支持允许、拒绝、超时和取消。
4. 实现 OMP 提问 UI，区分交互问题与权限请求。
5. 接通停止操作、运行状态与进程生命周期；用运行身份过滤晚到事件。
6. 以隔离示例仓库跑通“读取文件 -> 修改文件 -> 运行测试 -> 展示结果”，并验证拒绝写入和执行中取消。

交付：可使用的 OMP 对话、工具/审批 UI、代表性用户流程集成测试及针对跨进程边界的 E2E。

退出条件：不仅能显示回复，而且工具副作用、错误、拒绝和停止均与界面一致；原 Pi 流程仍通过对照验证。

## M4：会话、模型和可靠性

目标：可以关闭应用后继续工作，不混用项目、模型和数据。

步骤：

1. 实现引擎会话字段与版本迁移、原生会话路径/ID 映射、旧会话兼容。
2. 支持列表、名称、归档、打开和恢复。分支只在协议实验通过后开放。
3. 实现模型列表和设置投影、凭证受控注入与脱敏；明确桌面配置和 OMP 自动发现的优先级。
4. 验证流式中退出、OMP 崩溃、磁盘写失败、已丢失会话文件和模型不可用。
5. 支持按能力开放 follow-up/steer、压缩和思考级别，并处理不兼容模型切换。
6. 两个项目并发运行，前台切换不改变后台执行的 cwd 和权限范围。

交付：会话迁移、恢复、模型配置、凭证处理、错误恢复和并发项目测试。

退出条件：两次应用启动前后会话一致；没有双重写入、跨项目串流或执行自动重放。

## M5：OMP 差异能力与插件边界

按下面顺序逐项开放，每项均需能力证据和用户路径测试：

1. 子代理：生命周期、父子关系、进度、查看详情、取消与后台任务状态。使用 OMP 编排，不再同时调用桌面旧编排器。
2. OMP 工具：hashline/edit 的变更摘要、LSP 诊断、DAP 调试结果；先通用展示，再添加必要专用视图。
3. 配置生态：MCP、规则、技能和记忆，明确加载责任与项目/全局作用域，避免重复注册。
4. 桌面插件：先验证面板、主题和独立服务，再适配需要 Agent Tools、模型调用或 pi extension 的插件。
5. Plan/Goal：逐项比较现有桌面状态机与 OMP 行为，明确审批、模式转换和恢复，不仅映射同名按钮。
6. 高权限工具：browser/computer/eval 等只有权限边界和数据处理通过验收后才开放。

交付：可见的能力清单、已支持插件分类、差异功能说明、对应测试。

退出条件：每个开放入口有完整交互闭环；未支持项有准确状态，不出现可点击但无效或落到错误引擎的按钮。

## M6：打包、升级与跨平台

目标：交付脱离开发机全局依赖也能启动的 macOS arm64 安装产物。

步骤：

1. 决定固定 OMP 预编译产物，或打包 Bun + bridge + 目标平台原生模块；二选一的主路径写入 ADR。
2. 使用构建清单固定 OMP 版本、SHA/校验值、原生模块目标和桌面版本；生产环境不运行临时 `bunx` 下载 latest。
3. 配置 productName、appId、可执行文件路径、Resources/ASAR 外部资源、数据根、凭证存储命名和更新源。
4. 在不依赖全局 Bun/OMP 的环境启动，检查路径含空格/中文、离线启动、进程崩溃及退出清理。
5. 保留许可证和第三方声明；签名/公证需要的用户证书在真实发布时处理，不把开发构建冒充已签名版本。
6. macOS arm64 通过后，单独建立 Windows x64、Linux x64 任务，验证信号、原生模块、路径及权限语义差异。

退出条件：打包产物通过安装启动、对话、工具、取消、恢复烟测；未验证的平台明确标记不支持。

## M7：日常使用验收与维护交接

在真实但隔离的示例项目中做完整编码任务、并发任务、长会话和故障恢复。记录 UI 基线差异、剩余限制、性能与资源开销。

交付：发布检查单、用户说明、上游升级演练和回退记录。没有必要在 M7 前删除旧 Pi 引擎；是否移除取决于产品范围和维护成本。

## 全程变更规则

- 一个阶段可以分多个小任务，但一个任务应只有一个可验证的结果。
- 架构、权限或持久化契约变更同步 ADR、规格及测试，不只修改本工作区计划。
- 如果实验推翻原设计，先更新证据和后续任务，再实施；不要在错误假设上补丁累加。
- 准备提交时只暂存明确文件，用户要求提交后才提交；本轮规划不自动提交或推送。
