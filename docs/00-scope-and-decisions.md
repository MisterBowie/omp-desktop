# 项目范围与决策

## 1. 用户目标

开发一个 OMP 桌面端，初期界面和主要操作尽量保持 PI-Desktop 的体验；根据 OMP 能力增减功能。当前任务只负责规划、实现路径、详细说明及源码拉取，实际功能由用户选择其他模型执行。

“完全仿写”在本计划中解释为尽量保持可见交互和核心工作流，不表示重写全部源码，也不表示必须保留与 OMP 冲突的两套底层实现。

## 2. 已选择的路线

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 产品基础 | 基于 PI-Desktop 本地分支开发 | 复用窗口、布局、会话列表、工具展示、插件面板和打包基础设施 |
| OMP 接入 | 优先独立进程，先验证 rpc-ui + 受信扩展/原有审批，必要时增加 SDK bridge | 把运行时和原生依赖隔离在边界内 |
| 旧引擎 | 开发初期保留 Pi | 作为 UI 和执行行为的对照，便于定位回归 |
| 第一平台 | macOS arm64 | 与当前开发机器一致，先证明完整链路 |
| Node | NVM 管理的 Node 24 | 用户已确认可切换，已有 v24.14.0 |
| 首期界面 | 保留现有布局，补必要的状态与控件 | 控制初期改动范围 |
| OMP 特有能力 | 用能力清单逐项接入 | CLI 能做到不代表桌面接口已完整暴露 |
| 产品发布 | 开发验证后单独推进 | 用户已另行授权推送源码与计划到 MisterBowie/omp-desktop；不发布产品或创建 PR |

## 3. 产品阶段

### 接入验证版

可以选择 OMP，创建独立会话，发消息，显示流式文本、思考和工具结果，取消执行，重启恢复。工具执行有明确且经过验证的权限路径。此阶段不要求支持所有插件或高级面板。

### 可日常使用版

支持可靠的项目和会话隔离、模型配置、错误恢复、工具交互、必要的会话管理，以及 OMP 核心工具的可用展示。提供可以安装的 macOS arm64 构建。

### 功能完善版

按实际需求接入 OMP 子代理、LSP、DAP、记忆、MCP、规则、技能及相关 UI；在能力覆盖和打包通过后扩展平台。

## 4. 首期不做

- 从零重做桌面框架，或切换 Electron/React 技术栈。
- 重写 OMP 引擎、私有维护一套 OMP 业务分叉。
- 同时实现多个引擎的通用插件平台。
- 自动导入或覆盖用户现有的 Pi/OMP 历史会话及凭证。
- 未验证就承诺原有 `.piplug` 的 Agent Tools、pi extensions 全部兼容。
- 云同步、多人协作服务、远程部署和商业计费系统。
- 未经测试宣称原桌面的 Plan/Goal、沙箱或权限层对 OMP 全部有效。

## 5. 必须通过实验决定的事项

| 编号 | 问题 | 决定时点 | 默认处理 |
| --- | --- | --- | --- |
| D01 | 普通 RPC 是否足以承载工具审批、取消和完整事件？ | M1 | 能力不够时采用独立 SDK bridge，或对单独场景评估 ACP |
| D02 | OMP 完整会话使用的引擎、工具入口及运行时要求是什么？ | M1 | 依源码与实际运行确定，不把低层 Agent 包当完整 OMP |
| D03 | 会话内容由谁持久化？ | M1-M2 | OMP 保存原生会话；桌面保存索引、元数据和展示投影，先验证接口 |
| D04 | 权限政策由谁决策，如何阻断原生 OMP 工具？ | M1 | 复用桌面政策需有工具执行前阻断证据；否则设计明确的 OMP 政策桥接 |
| D05 | 原桌面 Plan/Goal、子代理、插件能力如何映射？ | M1、M5 | 未映射前在 OMP 会话中关闭对应入口并说明实际状态 |
| D06 | 模型目录、认证和配置能否受控注入？ | M1、M4 | 以桌面配置交互为入口，适配层单向投影，避免隐式读取用户全局配置 |
| D07 | 普通 RPC、rpc-ui、ACP 各覆盖哪些 OMP 能力？ | M1 | 记录逐项能力表，不能因为都是 JSON 就认为协议相同 |
| D08 | 是否需要彻底闭源对外发行? | 发布前 | 先按遵守 PI-Desktop LGPL-3.0 的 fork 路线规划 |

### M1 结项结论(2026-09-22)

依据 `docs/validation/M1-compatibility.md` 与 `docs/decisions/001-omp-transport.md`:

| 编号 | 结论 | 证据 |
| --- | --- | --- |
| D01 | 已定:普通 RPC(**rpc-ui 模式**)足以承载工具审批、取消和完整事件,不需要独立 SDK bridge | E01-E05、E10 |
| D02 | 已定:完整会话来自 `omp --mode rpc-ui` 子进程,不使用低层 Agent 包 | E01、E10 |
| D03 | 已定:原生会话由 OMP 保存在其 agent dir(JSONL + `sessionId`);桌面只保存索引、元数据与展示投影 | E06 |
| D04 | 已定:权限由受信扩展的 `tool_call` 钩子在做执行前决策;原生工具与宿主工具都在同一条钩子上被阻断 | E04、E08 |
| D05 | 部分:子代理事件、进度与快照已实测(含 `parentToolCallId` 父子关联);父子关系的 UI 映射与停止边界留待 M5/T17 | E08 |
| D06 | 部分:模型目录与配置已验证受控注入且不读用户全局配置;系统密钥存储命名留待 M4/T22 | E07 |
| D07 | 已定:rpc 与 rpc-ui 的能力差异已实测(仅 rpc-ui 提供 `ask` 工具);ACP/SDK 仅源码比对,未做运行时结论 | E10 |

## 6. 许可证与品牌

PI-Desktop 采用 LGPL-3.0；OMP 主项目采用 MIT，附带的第三方组件另有声明。对外分发时保留版权、许可证及相应源码提供等义务，按实际组合方式核对。商业使用与完全闭源不是同一个问题。

改名不改变派生代码的许可证义务。若商业目标要求所有修改都不向接收者提供源代码，应在投入大规模改造前重新评估许可路线或获取适当授权。

开发工作名为 OMP Desktop，不代表获得任何上游商标授权。产品图标、名称、应用标识、签名、更新源在发布阶段统一确定。

## 7. 成功标准

- 用户能从熟悉的 PI-Desktop 界面完成一个真实的 OMP 编码任务。
- 执行结果来自完整 OMP 能力，而不只是替换模型请求库。
- 每个会话的项目、权限、取消和恢复行为可解释且有测试覆盖。
- 可以锁定、升级和回退 OMP，运行时差异集中在少数模块。
- 交给下一模型时，任务有明确输入、输出、文件位置和验收条件。
